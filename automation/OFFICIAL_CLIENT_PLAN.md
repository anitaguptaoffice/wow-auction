## 战网与选角能省到什么程度

默认采用 attach-first：先识别已运行的正式客户端，再决定是否需要启动器。

| 客户端现状 | 入口动作 |
| --- | --- |
| 正确角色已进入世界 | 核实服务器、角色身份和插件版本，直接进入拍卖准备 |
| 正在角色选择页 | 定位目标角色并进入世界，不经过战网 |
| 正在载入 | 等待明确状态，不发送 Enter 或扫描键 |
| 游戏不存在，战网已登录 | 经正常启动流程启动一次官方客户端 |
| 认证过期或出现验证码 | 等待用户正常登录，恢复后接续任务 |

同一 WoW 子账号下，一次客户端启动服务整批角色；每个角色完成后 /logout，下一角色复用仍存活的客户端。切换 WoW 子账号和断线恢复属于不同流程，不承诺沿用同一会话。

冷启动时完全替代 Battle.net UI 是独立的可选研究：需要证实正常签发的游戏启动凭据如何交接给官方客户端。已有 ST、RealmListTicket、RealmJoinTicket、会话密钥用途不同；已通过 Python 探针认证，不证明任一材料能直接作为 Wow.exe 启动参数。当前不读取现有进程凭据，不将凭据放命令行、配置、日志或 Git，不把旧票据永久缓存。

选角可以由控制器代操作，但切换角色的登录和世界载入仍由官方客户端完成。游戏内插件在角色选择页不能承担正常插件逻辑。第一版不引入自建世界连接、客户端注入或 Lua unlock 来跳过选角。

## 桌面与输入方案

| 方式 | 设计判断 |
| --- | --- |
| 本机窗口模式，短暂切前台执行动作 | 第一阶段验证；扫描等待和归档时尽量不抢焦点。后台截图是否持续更新需实测 |
| Windows Win+Tab 虚拟桌面 / 虚拟显示器 | 可整理或承载窗口，但不会自动获得独立键鼠焦点，不能据此承诺纯后台操作 |
| PostMessage / ControlSend 到隐藏窗口 | 游戏是否接收及各场景表现未验证，不作为默认输入通道 |
| 虚拟鼠标 / HID 设备 | 不等于某个窗口的私有鼠标；本设计不安装驱动或以此解决隔离问题 |
| 独立物理采集机 | 与用户工作桌面隔离最直接；游戏和控制器在该机器的正常交互会话运行 |
| 虚拟机内运行游戏及控制器 | 技术候选；GPU、国服客户端兼容性、远程断开和锁屏后行为均需单独验证，不承诺可用 |

SendInput 写入系统输入流，并不接受目标 HWND。Windows 的 Win+Tab 工作区与 Win32 Desktop 对象也不是同一概念，二者均不能直接当作第二套独立输入系统。现有 runner 明确恢复并聚焦窗口，没有纯后台输入能力。

因用户关注账号风险：运行官方 exe 只改变协议实现方式；外部软件无人值守循环选角、按键仍是自动化行为，不因此获得官方许可。先提供人工触发与自动归档模式，循环控制作为明确区分的可选模式；不以隐藏窗口或设备伪装降低检测为设计目标。

## 每个角色的状态机

```text
识别当前客户端状态
  → 定位并核对目标角色 → 进入世界 → 核对角色/服务器/本轮 ID
  → 拍卖师交互 → 确认 AUCTION_HOUSE_SHOW
  → 显式触发一次扫描 → 等待快照 → 分批处理 → 完整性状态确认
  → 正常 /logout → 确认返回选角页
  → 等待角色级 SavedVariables 稳定 → 复制并验证 → 原子归档
  → 将归档加入上传队列 → 下一个角色
```

- 用户先把角色停在拍卖师可交互范围；第一阶段不做寻路。
- 沿用滚轮向下交互、1 键 /logout。扫描使用独立固定宏键或 /as scan；交互完成后才触发，不能仅等待固定 500ms。不承诺一个宏自动完成受保护交互及全部异步步骤。
- 可设计显式的一次性“准备扫描”按钮：收到下一次正确的 AUCTION_HOUSE_SHOW 后消费一次授权。普通打开拍卖行仍不自动扫描，重复事件不得重复请求。
- 用角色名+服务器身份定位，列表序号仅作定位提示；战团列表排序变化不得导致扫错角色。
- 新增 run_id、character、realm、auction_open、scan_started_at、phase、记录数量、scope_complete 等可观察字段。AS_READY 仅表示插件已就绪，不能当作拍卖行已经打开。
- OCR 必须校验本轮身份与新状态。现有“必须看见 SCANNING 才接受 COMPLETE”可能漏掉很快的扫描；用本轮 ID 和时间戳消除旧面板误判，而不是增加连续按键。
- 只有新快照核心记录完整、必要的市场范围补全过程结束，才允许小退。范围仍未知时显式标记 unknown，不能冒充全服或本服。
- 等待超时、断线、NPC 不可交互、权限错误时停止当前操作并保存诊断；不通过重登录或换角色循环冲击接口。

## 数据交接与内存

主路径使用角色级 SavedVariables。既然每个角色本来就要小退，就由游戏正常写文件，不额外走 /as export、内存读取或 TTS；游戏仍会执行自身保存序列化，不能承诺零序列化或瞬间完成。

文件接收条件：返回选角页，源文件出现本轮变化，读取前后长度/修改信息稳定，Lua 解析完整，快照角色与服务器匹配本轮任务，扫描时间新鲜，条数一致，核心缺失和 API 错误计数为零。稳定时间不是完整性证据，解析和业务检查必须通过。

通过后立即复制到不可变归档，计算内容 SHA-256，并由外部进程压缩。临时文件验证后原子重命名，历史归档永不因新快照自动删除。上传失败保留归档并重试上传，不重新扫描。

角色在本轮只访问一次。为了复用客户端，默认不在游戏运行期间改写其 SavedVariables。当前 runner 只在最终自然退出后清理已核验源文件，这一保守规则继续保留；整批最后退出一次可避免下批登录再加载大快照。长驻客户端与清理旧角色快照的组合，另做专门生命周期验证。

## 调度与网站发布

- 排队以市场和正常权限账号为单位；避免同一连接区的多个角色重复扫描。
- 精确限流范围及冷却不能从“等待”标签推断。按已观察的账号/游戏账号和市场记录请求、成功及失败时间，保守串行调度，遇无响应暂停；不承诺换角色就有新额度。
- 归档与后续网络上传分离，下一角色可以在本地归档成功后继续，网站暂时失败不丢失已采集数据。
- 新 compact-market 发布链：验证归档 → 上传 → 从历史归档集构建新 generation → 校验数量、市场范围和时间 → 服务健康检查 → 切换版本；失败保留当前线上版本。当前不可变构建器不能当作已支持热增量导入。
- 角色、来源服务器、采集时间随快照保留；区域共享商品与本服物品遵循插件标记。只有完整快照能用于判断某个市场的挂单消失，失败和空响应不得覆盖线上数据。

## 实施顺序与验收

1. 修正 runner 的 attach-first、拍卖开启状态门禁、角色身份和本轮标识；保留人工操作入口。当前 bootstrap 会在 WoW 已运行但战网未运行时仍启动战网，需要调整分支顺序。
2. 单角色验证：登录 → 交互 → 一次扫描 → 小退 → 归档完整；期间不运行独立协议探针。
3. 两角色验证：仅启动一次客户端，依次归档两个角色，身份/服务器不串；任一阶段失败都不处理下一角色的按键。
4. 验证普通后台等待、遮挡、最小化、锁屏和远程断开分别如何影响输入与截图。未通过的环境明确停止，不用“SendInput 返回成功”代替游戏状态成功。
5. 接入 compact-market 上传和发布适配器；先核对候选数据再切线上。

这次只完成代码同步、证据核对和设计，未修改运行中的插件、凭据、键位或 Windows 桌面配置，未启动实机自动采集。
