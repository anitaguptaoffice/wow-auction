# 只读内存快照接收器（插件 2.8.0）

启动：在项目根目录运行 `./game/memory-bridge/Start-Receiver.ps1`。
默认游戏路径为 `F:\World of Warcraft\_retail_\Wow.exe`，可通过 -GameExe 指定。
接收网页：http://127.0.0.1:8766，仅监听本机。关闭接收器终端即可停止。

流程：

1. 启动接收器，重启客户端，登录角色。程序自动识别匹配完整路径的 WoW 进程。
2. 打开拍卖行，手动开始扫描。扫描完成后点击“导出到电脑”。
3. 插件序列化完整快照，分块校验、发布；接收器验证活动心跳后读取。
4. 网页显示“校验通过、已保存”才算传输成功，可停止游戏中的剩余发布。
5. 后续扫描直接重复以上流程，不需要小退。换角色、/reload、重启会重新定位。

文件保存于 `data/memory-export/<session>/snapshot.lua`，沿用现有导入格式；
逐块文件、状态和完整文件都保留，程序不会删除历史导出。清单声明的条数与完整快照字段均被保留。
传输完整性与拍卖数据完整性不同：入库前仍使用 backend 的 validate_snapshot 检查服务器、
条数、缺失计数等。接收器不执行 Lua，不自动上传网站。

## 稳定性与边界

- 只调用 Windows 查询/读取 API；不写游戏内存、不注入、不挂调试器、不改保护、不提权。
- 固定两元素 Lua 数组：数字锚点 + 完整帧字符串。字符串不可变，单次赋值发布。
- 不缓存字符串地址，每次从槽位重读指针；读前后指针和头部不一致时丢弃本次读取。
- 首次定位必须观察到同一会话的序号递增，排除静态旧副本。5 秒无新帧则重新定位。
- 候选布局经过前缀、长度、边界和校验检查；不硬编码本机绝对地址。
- 序列化按约 5ms 时间片让出，校验也分批让出。导出期间禁止启动新扫描。
- 不压缩；原始块额外占用接近序列化后的大小（当前实测快照约 154 MiB），为了补发保留至新扫描/清理。
- 发布间隔至少 50ms，256KiB/块，重复 3 轮；低帧率会延长时间。每 16 个队列项和首尾重复清单。
- 单向只读，没有外部 ACK。游戏进度不能表示落盘完成；电脑端收齐且全量长度/Adler 校验正确后，
  fsync 并原子替换最终文件，记录 SHA-256。损坏或缺块时不会发布最终文件。
- 接收器重启会重新校验磁盘块，坏块隔离为 .bad，等待再次发布。游戏同一会话仍可补发；
  若游戏重载导致源会话丢失，重新导出会建立新会话，不混用旧块。
- 缺块时运行 `/as resend all`，或 `/as resend 18,93`。地址布局不兼容时只报告未找到，不猜测读取。
- 最大 8192 块（2GiB）。接收器会拒绝超界协议；普通快照远低于此限值。

## 验证

`.venv/Scripts/python.exe -m unittest discover -s game/memory-bridge -v`

覆盖实际 Lua 发送器与导入器、漏块/乱序/重复、重启补传、磁盘损坏、整份校验失败、
会话隔离、读取途中指针变化，以及自有 Windows 子进程中的真实只读读取和地址迁移。

2026-10-29 离线真实快照：391,055 条，6,279,123 个字段逐一一致，
161,425,997 字节、616 块。离线回放不代表实机速度；2.8.0 的重启后完整游戏流程仍待用户验收。

定位思路参考 [BabelChat](https://github.com/Yumash/BabelChat)，本实现独立编写。
先前当前国服客户端的 1 MiB 标记数据及更新跟踪已实测通过；
这不等于所有后续游戏版本都已验证。
